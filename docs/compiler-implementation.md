# 编译器实现指南

> 状态：实施草案（Draft）  
> 相关文档：[语言设计说明](language-design.md)

当前实现详情见[已实现功能参考](implemented-features.md)，未完成里程碑及验收标准见[实现路线图](roadmap.md)。

本文档给出编译器从零开始的实现路线。目标不是一次实现全部语言能力，而是持续维护一条可以测试的完整编译链路，每个里程碑结束时都能得到明确结果。

## 1. 实现原则

### 1.1 先完成最小垂直切片

不要先写完整语法分析器，再写完整类型系统，最后才尝试生成代码。正确顺序是先让最小程序贯穿所有阶段：

```dc
fn main() {
}
```

第一条链路只需要完成：

```text
读取文件 -> 解析 main -> 检查入口 -> 生成目标文件 -> 链接 -> 成功运行
```

链路打通后，再沿同一条链路逐项增加表达式、变量、控制流和函数。这样可以尽早验证各阶段之间的数据结构是否合理。

### 1.2 前端与后端分离

词法分析、语法分析和类型检查不能直接依赖 Cranelift 类型。编译器前端先生成自己的中间表示，再由后端把中间表示转换为 Cranelift IR。

```text
源码 -> AST -> HIR -> IR -> Cranelift
```

- AST 保留源码的语法结构和位置。
- HIR 保存名称解析结果和确定后的类型。
- IR 使用更少、更简单的指令表达控制流和运算。
- Cranelift 后端只负责把 IR 转换为机器码。

这种边界可以避免未来增加解释器、LLVM 或 WebAssembly 后端时重写语言前端。

### 1.3 错误必须携带源码位置

所有 Token、AST 节点和用户可见错误都应携带 `Span`：

```rust
struct Span {
    file: FileId,
    start: u32,
    end: u32,
}
```

`start` 和 `end` 建议使用 UTF-8 字节偏移。行号和列号只在展示错误时通过源码索引计算，避免每个节点重复存储。

### 1.4 第一版只编译当前平台

第一版只要求在运行编译器的操作系统和 CPU 上生成程序，不立即支持交叉编译。先固定一套平台 ABI 和链接方式，完成 MVP 后再抽象目标平台。

## 2. 推荐技术方案

- 实现语言：Rust。
- 语法分析：手写递归下降解析器。
- 表达式解析：Pratt Parser 或优先级爬升算法。
- 代码生成：Cranelift。
- 输出方式：生成系统目标文件，再调用系统链接器。
- 测试：Rust 单元测试、编译测试和端到端运行测试。

第一版建议手写词法分析器和解析器。当前语法规模不大，手写实现便于精确控制错误恢复和错误信息，也能减少语法规则被第三方解析框架限制的风险。

## 3. 推荐仓库结构

开始时使用单个 Rust package 即可，不需要过早拆成多个 crate：

```text
.
├── Cargo.toml
├── README.md
├── docs/
│   ├── language-design.md
│   └── compiler-implementation.md
├── examples/
├── runtime/
│   └── src/
└── src/
    ├── main.rs
    ├── lib.rs
    ├── cli.rs
    ├── source.rs
    ├── diagnostic.rs
    ├── token.rs
    ├── lexer.rs
    ├── ast.rs
    ├── parser.rs
    ├── symbol.rs
    ├── resolve.rs
    ├── types.rs
    ├── typecheck.rs
    ├── hir.rs
    ├── ir.rs
    ├── lower.rs
    ├── codegen.rs
    ├── linker.rs
    └── driver.rs
```

各模块职责：

| 模块 | 职责 |
| --- | --- |
| `source` | 加载源码、分配 `FileId`、计算行列位置 |
| `diagnostic` | 收集并展示错误、警告和源码片段 |
| `token` / `lexer` | Token 定义和词法分析 |
| `ast` / `parser` | AST 定义和语法分析 |
| `symbol` / `resolve` | 符号表、作用域、模块和名称解析 |
| `types` / `typecheck` | 类型表示、推断、转换和类型检查 |
| `hir` | 保存已经解析名称并确定类型的程序 |
| `ir` / `lower` | 构造适合代码生成的控制流 IR |
| `codegen` | 使用 Cranelift 生成目标文件 |
| `linker` | 调用系统链接器并加入运行时库 |
| `driver` | 按正确顺序组织整个编译流程 |
| `cli` | 解析命令行参数并调用编译驱动 |

模块数量是目标结构，不要求第一天全部创建。只在某一阶段真正需要时再增加对应文件。

## 4. 编译器命令设计

第一版建议提供一个名为 `dc` 的命令：

```text
dc check <project>   只执行前端检查
dc build <project>   编译并链接可执行文件
dc run <project>     编译并运行程序
```

建议约定：

- `<project>` 默认是当前目录。
- 项目源码位于 `<project>/src`。
- 构建产物位于 `<project>/target`。
- `check` 不调用代码生成器和链接器。
- `build` 成功时返回退出码 `0`，失败时返回非零值。
- `run` 把程序参数和退出码正确传递给生成的程序。

M9 实现前仍使用项目目录名作为默认输出文件名；M9 引入 `dolphin.toml` 后，由项目清单稳定描述 `group:name:version` 包坐标、源码目录和可执行目标。包管理器和远程依赖不属于 M9。

## 5. 核心数据结构

### 5.1 Token

Token 至少包含种类和源码范围：

```rust
struct Token {
    kind: TokenKind,
    span: Span,
}
```

标识符和字符串内容可以先使用源码切片，需要跨阶段长期保存时再放入字符串池。

### 5.2 AST

AST 应描述用户写出的结构，不在解析阶段执行类型检查：

```text
Program
  Module
    Function
      Parameters
      ReturnType?
      Block
        Statement*
```

表达式节点至少包括：

- 字面量。
- 名称引用。
- 一元和二元运算。
- 赋值。
- 函数调用。
- 数组字面量和下标。
- 条件表达式。

### 5.3 符号和作用域

不要把字符串名称直接作为后续阶段的唯一标识。名称解析成功后，为每个声明分配稳定 ID：

```text
ModuleId
FunctionId
LocalId
```

后续 HIR 通过 ID 引用声明，可以正确处理同名变量、内层遮蔽和跨模块调用。

### 5.4 类型

第一阶段可以使用以下内部类型：

```text
Unit
Bool
Char
String
Int(signed, bits)
Float(bits)
Array(element, length)
Function(params, return)
Error
```

`Error` 是错误恢复类型。表达式发生类型错误后返回 `Error`，可以减少由同一个根因引发的大量级联错误。

### 5.5 自定义 IR

IR 不需要一开始设计成通用优化框架，只需能表达：

- 常量和局部值。
- 算术、比较和类型转换。
- 基本块和条件跳转。
- 函数参数、调用和返回。
- 数组地址计算和边界检查。
- 调用运行时函数。

每个函数由多个基本块组成，每个基本块必须以跳转、条件跳转或返回结束。不要让代码生成器直接递归遍历 AST 生成机器码，否则循环、短路逻辑和后续优化会变得难以维护。

## 6. 分阶段实施计划

### 阶段 0：冻结最小语法

先从完整语言规范中选出第一个可实现子集：

```dc
fn main() {
}
```

需要确定：

- 源文件使用 UTF-8。
- 空白和注释规则。
- `fn`、标识符、括号和代码块 Token。
- `main` 入口规则。
- 当前平台上的输出文件位置和命名。

完成标准：为这个最小子集写出明确语法和至少一个正确、一个错误示例。

### 阶段 1：源码管理、诊断和词法分析

实现：

- `SourceMap` 和 `FileId`。
- 字节偏移到行列号的转换。
- 关键字、标识符、字面量、运算符和标点 Token。
- 单行和多行注释。
- 非法字符、未闭合字符串和未闭合注释错误。

词法分析器不应直接打印错误，而是返回 Token 和诊断信息，由编译驱动统一决定是否继续。

完成标准：

- 能输出示例程序的 Token 序列。
- 每类 Token 都有单元测试。
- 非法输入能准确标出文件、行和列。
- 词法分析器不会因普通用户输入而崩溃。

### 阶段 2：语法分析和 AST

先实现：

- 函数定义。
- 参数和返回类型。
- 代码块。
- 变量声明、表达式语句和 `return`。
- 字面量、名称、调用和基础运算表达式。

随后再加入数组、`if` 和循环。解析器遇到错误后应跳过到分号、右花括号或下一个顶层声明，尽量在一次编译中报告多个独立错误。

完成标准：

- 正确程序生成稳定 AST。
- 运算符优先级测试覆盖所有优先级层级。
- 缺失分号、括号和花括号时给出明确错误。
- 错误输入不会导致无限循环或崩溃。

### 阶段 3：项目、模块和名称解析

实现项目源码发现：

- 扫描项目的 `src/` 目录。
- `src/*.do` 归入根模块并允许省略 `pkg`。
- 子目录文件必须声明与相对路径一致的 `pkg`。
- 收集函数和其他顶层声明。
- 处理 `use` 和 `pub`。
- 为函数、参数和局部变量分配稳定 ID。
- 检查重复声明、未知名称和不可见成员。

名称解析建议分两遍：第一遍收集所有模块和顶层声明，第二遍解析函数体。这样函数可以调用定义在后面的函数。

完成标准：

- 模块示例可以解析 `std.math` 和 `math.min`。
- 错误模块路径、重复名称和私有访问均有测试。
- 局部变量遮蔽行为符合语言规范。

### 阶段 4：类型检查和 HIR

按以下顺序增加类型能力：

1. `i32`、`bool` 和无返回值函数。
2. 函数参数、返回值和函数调用。
3. 其他整数和浮点类型。
4. `var`、`val`、赋值和显式转换。
5. 数组、字符串和字符。

局部类型推断只根据初始化表达式进行，不做全局或跨函数推断。每个 HIR 表达式都应保存最终类型和对应的 `Span`。

完成标准：

- 所有 HIR 表达式都有确定类型或 `Error` 类型。
- 函数的每条可达路径都满足返回规则。
- 不可变变量赋值、错误参数数量和错误类型均有诊断。
- M2/M3 的变量与控制流前端测试能够成功结束。

### 阶段 5：最小 IR 和代码生成

代码生成按以下顺序推进：

1. 空 `main` 函数。
2. `i32` 常量和返回值。
3. 整数算术与比较。
4. 局部变量和赋值。
5. `if`、`loop`、`while` 和 `for`。
6. 用户函数调用。
7. 数组和运行时边界检查。

第一步只要求生成当前平台的目标文件。代码生成器接收已经完成名称解析和类型检查的 IR，不再处理“名称是否存在”或“类型是否匹配”。

完成标准：

- 生成的目标文件可以被系统链接器接受。
- 空程序能够启动并正常退出。
- 算术和控制流结果与语言语义一致。
- 同一份 IR 可以稳定生成相同的可观察行为。

### 阶段 6：链接器和可执行文件

实现：

- 根据当前平台选择目标格式。
- 将目标文件传给系统链接器。
- 捕获并转换链接器错误。
- 把产物放入项目 `target/` 目录。
- 避免把临时目标文件写入源码目录。

第一版不需要自己实现链接器。编译器应把调用系统工具的细节封装在 `linker` 模块中，避免散落在代码生成逻辑里。

完成标准：`dc build <project>` 能生成一个无需解释器即可启动的本机程序。

### 阶段 7：最小运行时和标准库

字符串、格式化输出和进程功能需要少量运行时支持。先定义稳定的内部 ABI，再实现：

- 程序入口适配。
- UTF-8 字符串的指针和长度表示。
- `print` 和 `println`。
- 整数、浮点、布尔值和字符格式化。
- 越界、除零和溢出的终止函数。

运行时函数使用编译器内部保留名称，用户源码不能直接声明相同符号。运行时 ABI 属于实现细节，不应暴露为语言语法。

完成标准：基础示例可以打印预期内容，运行时失败可以输出错误原因并返回非零退出码。

### 阶段 8：完整 MVP 和稳定化

补齐语言设计文档中列出的 MVP，并集中处理：

- 多文件编译顺序。
- 循环中的 `break` 和 `continue`。
- 短路逻辑。
- 条件表达式。
- 数组初始化和边界检查。
- 格式字符串占位符检查。
- 无效程序的错误恢复。

完成标准：

- 当前里程碑及之前的 `examples/mN` 均可构建和运行。
- 所有已记录语法都有正向和错误测试。
- 编译器对错误输入不发生 panic。
- 语言规范、示例和实现保持一致。

## 7. 建议的迭代顺序

不要按照语言设计文档的章节顺序实现。推荐使用以下可运行增量：

| 里程碑 | 新增能力 | 可验证结果 |
| --- | --- | --- |
| M0 | 空 `main` | 生成并运行空程序 |
| M1 | `i32`、算术、返回值 | 程序返回计算结果 |
| M2 | 局部变量、`var`、`val` | 检查赋值和不可变规则 |
| M3 | 比较、`if`、`loop`、`while` | 运行包含分支和循环的程序 |
| M4 | 参数和函数调用 | 编译并运行 `add(1, 2)` |
| M5 | 最小运行时和 `println` | 输出整数和字符串 |
| M6 | 数组和 `for` | 运行基础示例 |
| M7 | `src`、`pkg`、`use`、`pub` | 运行模块示例 |
| M8 | 其余基础类型和完整诊断 | 达到 MVP |
| M9 | `dolphin.toml` 项目清单 | 通过 `group:name:version` 坐标和稳定配置描述项目 |
| M10 | 平台与工具链抽象 | 链接流程不再硬编码 Unix/`cc` 假设 |
| M11 | Windows x86_64 | 在 Windows CI 构建并运行全部 MVP 示例 |
| M12 | 自包含工具链与发布 | 无需系统 C 编译器并自动生成三平台发行包 |
| M13-M16 | 数据类型、内存模型、泛型与优化 | 逐步形成可编写实际应用的语言与工具链 |

每个里程碑都应同时提交实现、测试、示例和必要的文档更新。

当前实现状态：M0 到 M12 已完成。实现位于[仓库根目录](../)；多错误恢复和 DWARF 源码调试信息明确延后。

M9-M12 的优先级高于新增语言语法。先用项目清单稳定构建输入，再稳定平台 ABI、运行时和发行方式，可以避免结构体、动态容器等新能力建立在仍会变化的项目与链接边界上。详细任务与验收标准见[实现路线图](roadmap.md)。

第二阶段的关键依赖顺序为：

```text
项目清单(M9) -> 平台抽象(M10) -> Windows ABI(M11) -> 内嵌运行时、LLD 与发布(M12)
```

其中 Cranelift/LLVM 负责把 IR 转为目标文件，LLD/系统链接器负责把目标文件与运行时组合成可执行文件。是否内嵌链接器，与是否采用 LLVM 后端是两个独立决策。M12 应先保留 Cranelift，以较小改动验证自包含发行；LLVM 后端延后到 M16，用性能基准决定其价值。

## 8. 测试策略

### 8.1 单元测试

适合测试局部规则：

- 字符到 Token 的转换。
- 运算符优先级。
- 类型兼容性。
- 模块路径推导。
- 字节偏移到行列位置的转换。

### 8.2 编译测试

为每个语言规则准备正确和错误源码：

```text
tests/
├── pass/
│   ├── variables.do
│   ├── functions.do
│   └── loops.do
└── fail/
    ├── immutable_assignment.do
    ├── unknown_name.do
    └── type_mismatch.do
```

`pass` 文件必须编译成功；`fail` 文件必须失败，并检查主要错误代码、位置和关键信息。错误测试不要完整匹配操作系统路径或终端颜色。

### 8.3 端到端测试

端到端测试执行以下步骤：

1. 创建隔离的临时项目。
2. 编译源码。
3. 运行生成的可执行文件。
4. 检查标准输出、标准错误和退出码。

至少覆盖空程序、算术、分支、循环、函数调用、运行时错误和多模块程序。

### 8.4 回归测试

每次修复编译器 bug 时，先提交一个能够稳定复现问题的测试，再修改实现。解析器和类型检查器不应该因为用户输入错误而 panic；模糊测试可以在 MVP 后加入。

## 9. 错误处理约定

编译器内部错误和用户源码错误必须分开：

- 用户错误转换为 `Diagnostic`，正常结束编译流程并返回失败状态。
- 文件读取、链接器启动等环境错误返回结构化错误。
- 只有违反编译器内部不变量时才允许 panic，并视为编译器 bug。

每类稳定错误建议分配错误代码，例如：

```text
E0001 非法字符
E1001 未知名称
E2001 类型不匹配
E3001 main 函数缺失
```

错误代码一旦公开，应尽量保持含义稳定。

## 10. 开始实施前的检查清单

开始写编译器代码前，先完成以下事项：

- [ ] 确认第一条垂直切片只支持空 `main`。
- [ ] 把最小子集写成明确的语法规则。
- [ ] 确认首个支持平台和系统链接器。
- [ ] 确定 `Span`、Token 和 AST 的基本结构。
- [ ] 为正确与错误的最小程序建立测试目录。
- [ ] 初始化 Rust package 和基础 CI。

第一条垂直切片完成后：

- [ ] 空程序能生成并运行。
- [ ] 无 `main` 和重复 `main` 能得到源码级错误。
- [ ] 编译器对非法字符、缺失括号和缺失花括号不会崩溃。
- [ ] 构建产物只写入 `target/`。
- [ ] README 中记录真实可用的构建命令。

## 11. 暂时不要做的事情

在 M0 到 M4 期间，不要提前投入以下工作：

- 包管理和远程依赖下载。
- 自己实现链接器。
- 跨平台交叉编译。
- 复杂优化和寄存器分配。
- 泛型、结构体、类和面向对象系统。
- 垃圾回收和复杂所有权系统。
- IDE 协议、格式化器和调试器。

这些能力都可能有价值，但不会帮助第一条本机编译链路跑通。MVP 稳定后，应根据真实示例和性能数据决定下一阶段，而不是同时扩展所有方向。
