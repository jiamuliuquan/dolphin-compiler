## 1. 历史用法：一次只给模型一个批次

当时先实现 M14-A–F，再完成 M15-A/B，最后完成 M15-C–F。本指南的 R00–R21 是这些已完成阶段的细分工作批次，不另造里程碑。以下保留当时每批的输入与执行规则，正文“新增”“待新建”“尚未实现”均按历史语境阅读，不能用于判断当前能力缺失。

执行规则：

1. 先读 AGENTS.md 及任务相关且实际存在的引用；引用缺失如实报告，不臆造项目规则。
2. 用 `git status --short` / `git diff` 确认现有改动；未经要求不还原用户文件、不提交、不推送。
3. 先审计 M13 基础和已验收的前置批次，再新增能力；不恢复已清理的 M14/M15 代码，不整体重写编译器。
4. 每批必须有可执行验收，包含正确用法、错误用法和边界；遇到前置能力缺失先补前置，不把验收点改成“未来支持”。
5. 只实现 v2 语义。M13 不存在的全局 allocate/free、资源 try 和旧泛型/标准库 API 不提供兼容层。
6. 某批失败不勾选完成，记录失败测试、原因和下一步。不要把“有 AST 节点”“能跑单个示例”当成语言特性完成。
7. 最终 IR 不得含未知类型/未展开泛型；后端不可用名字猜 Vec/Option/Iterator 身份。
8. 源码路径、类名与结构以实际仓库为准；以下入口是定位提示，不是禁止重构的白名单。

## 6. 每批的验证方式

以下是归档批次的验证方式，命令保留当时形式，不代表当前 workspace/feature 的完整检查集。当前任务按新计划及实际 CI 选择检查；不要为文档维护运行发行构建：

```text
cargo fmt -- --check
cargo clippy --all-targets -- -D warnings
cargo test
cargo build --release --bins
```

根据当前批次补充：

- 编译运行本批 .do 示例，检查 stdout/stderr/退出方式。
- M14 FFI 用真正 C fixture 校验调用/布局；本机无法执行的目标必须由对应平台 CI 验证，不冒称跨平台已通过。
- 内存验收用可注入分配失败/分配计数，避免通过耗尽机器内存验证 OOM。
- 不执行未定义行为并断言 Release 一定崩溃；只对规格保证的路径作稳定断言。
- 包管理测试使用独立临时 DOLPHIN_HOME、临时仓库和 loopback 服务；不依赖真实网站，不使用真实发布 token。
- 本机生成临时项目/归档/fixture 时使用测试临时目录，不修改用户全局仓库/缓存。
- 只有文档编辑时执行 diff/链接/一致性检查即可；不能把尚未运行的目标示例写成“验证通过”。

## 9. 最终用户验收脚本的故事线

这是已完成 M14/M15 闭环的历史验收故事线，也可用作后续回归场景；它不是尚未实现的任务列表，也不证明发行包已在无 SDK 的干净机器验收。

1. 在 lib 项目写 public 普通函数、泛型函数和使用 C 静态库的包装函数。
2. `dc build --lib` 得到可用标准 ZIP 工具打开的 `.dlib`；检查内含源码、清单和对应目标的 C 附件。
3. 将 dlib+sha256 发布到 file 仓库，再用同一目录通过 HTTPS 提供读取。
4. 在完全独立 app 中仅写 repository、坐标 dependency 和 use，构建运行，得到预期输出。
5. 在 app 使用作者没有实例化过的泛型类型，验证模板跨包编译。
6. 使用 Vec/String/CString、defer 与真实 C 调用，Debug 正常退出无用户分配泄漏。
7. 把 app 锁文件纳入版本管理后断网，以 `--locked --offline` 再运行；验证没有网络请求。
8. 人为修改归档/版本/目标后得到清晰失败；恢复正确输入再次成功。

以上故事线成立，才同时证明手动内存模型、API 易用性、C 互操作和类 Maven 发布消费流程真正接通。
