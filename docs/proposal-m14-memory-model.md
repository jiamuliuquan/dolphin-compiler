# M14 设计提案：内存模型与动态数据

> 状态：草案（Draft，待评审）  
> 对应路线图：[roadmap.md](roadmap.md) 第 6 节「M14：内存模型与动态数据」

本提案为 M14 里程碑冻结内存模型提供决策依据。在提案通过前，不进行实现；提案通过后，M13 已实现的结构体按最终语义对齐，不留半成品。

---

## 1. 背景与现状

当前编译器（M0-M13）处于**无堆**状态：

- 字符串是「指针 + 长度」的 fat pointer，但指针只指向编译期静态数据（见 [codegen.rs `emit_string`](../src/codegen.rs)，直接引用静态数据段），不存在堆分配与释放。
- 数组是定长值类型 `Array { element, length }`，直接平铺在栈/寄存器上。
- 结构体/枚举是纯值类型，按分量展开（`component_layout`），当前**不能**作为函数参数或返回值（见 [lower.rs](../src/lower.rs) 的 M14 占位诊断）。
- 运行时（[unix_runtime.c](../runtime/unix_runtime.c) / [windows_runtime.cpp](../runtime/windows_runtime.cpp)）仅提供 I/O 与字符串比较，不含任何分配函数。

因此，M14 的本质是**首次为语言引入堆**。本提案的核心是决定：堆内存由谁分配、谁释放、如何避免泄漏/重复释放/悬垂引用，以及结构体跨函数传递时的复制语义。

---

## 2. 设计原则（已确定）

以下原则由项目负责人明确，作为本提案的不可动摇前提：

1. **易用性优先**：语言面向学习与实践，用户心智负担优先于极致性能。
2. **零生命周期符号**：明确拒绝 Rust 式显式生命周期标注（`'a`、`'b`、`&mut` 满屏）。内存管理对用户尽量透明或低负担。
3. **显式控制，确定性释放**：采用 Zig 式「显式分配 + 确定性释放」哲学，不引入隐式分配、不引入 GC，也不引入 Rust 式所有权/借用检查。唯一的受控例外：字符串拼接运算符 `+` 作为语法糖隐式分配目标缓冲（见 §12.3 子问题 3b），其余动态内存一律显式 `allocate`；释放始终确定性显式。

---

## 3. 路线选择（已确定）

在所有权（Rust）、引用计数（RC）、垃圾回收（GC）、显式分配（Zig/C）四条路线中，选定 **Zig 式显式控制**。理由：

| 路线 | 符号负担 | 易用性 | 实现难度 | 结论 |
|------|---------|--------|---------|------|
| Rust 所有权 + 借用检查 | 高（`'a` 满屏） | 差 | 极高 | ❌ 违背原则 1、2 |
| 引用计数 RC | 零 | 高 | 中 | ❌ 需处理 null、循环引用，复杂度上升 |
| 垃圾回收 GC | 零 | 高 | 高 | ❌ 运行时复杂，违背「简单可维护」 |
| **显式分配（Zig 式）** | 零 | 中-高 | 低 | ✅ 选定 |

**核心立场：引用 = 显式指针/切片值，不引入隐式共享。**

Zig 式路线的关键洞察在于：结构体/枚举一律为值类型（赋值、传参即复制），「共享」必须通过显式指针 `*T` 或切片 `[]T` 表达。指针与切片本身都是**值**（一个地址，或「指针 + 长度」二元组），复制它们只是复制这两个字段，不产生「多个变量隐式共享同一可释放对象」的情况。

正因如此，**本语言不需要 RC 或 GC**——不存在隐式共享，释放时机始终由程序员用 `defer`/`free` 明确控制。评审期间一度考虑过的「引用共享 + RC」路线，因其连锁引入 null 设计、循环引用处理与运行时开销，且违背「显式控制」原则，最终排除。

## 4. 用户层控制粒度（已确定）

在「完全显式 allocator / 显式分配 + defer 糖 / 裸 malloc-free」三种粒度中，选定 **显式分配 + defer 语法糖**：

- 提供内建全局分配器，用户无需显式传递 allocator 参数。
- 提供 `defer` 语句，实现确定性释放。
- 提供 `try(...)` 作为 `defer` 的语法糖，覆盖「局部申请、用完即弃」的高频场景。
- 不引入 `Allocator` 类型与参数传递（保留为未来可演进项，见 §9）。

### 4.1 释放机制最终形态：`defer` 核心 + `try` 语法糖

经评审，**不采用** Java 式 `try-with-resources` 作为独立自动释放机制。原因：try-with-resources 要求资源「出块自动释放」，与本语言「堆内存必须能跨函数返回」直接冲突（自动释放会把返回给调用者的内存释放掉，产生悬垂指针）；且 Java 该机制依赖异常与 GC 兜底，本语言两者皆无。

最终形态为**两层**：

**第一层：核心机制 `defer <expr>`** —— 通用收尾，把一条语句推迟到所属作用域退出时执行：

```dc
fn do_something() {
    var buf = allocate(128);
    defer free(buf);        // 任何退出路径（含提前 return）都会执行
    // ... 使用 buf ...
}
```

`defer` 不限于释放内存，可推迟任意收尾动作（`defer close(f)`、`defer release(lock)` 等）。

**第二层：语法糖 `try(...)`** —— 等价于「`defer free` + 一个块」，用于局部资源「声明即绑作用域」：

```dc
fn do_something() {
    try (var buf1 = allocate(128), var buf2 = allocate(128)) {
        // ... 使用 buf1、buf2 ...
    }
    // 出块：自动 free(buf2) 再 free(buf1)（逆序）
}
```

`try(...)` 是纯语法糖，内部展开为：

```dc
var buf1 = allocate(128); defer free(buf1);
var buf2 = allocate(128); defer free(buf2);
{ /* 块体 */ }
```

### 4.2 `try` 资源禁止逃逸

`try(...)` 括号内声明的变量（`try` 资源）的生命周期被绑定到该块，**禁止逃逸出块**。若逃逸，编译器在 lowering 阶段报编译期错误。

本语言在 `try` 块内对资源采用**「禁止重新绑定/传播」**规则——不是事后追踪资源「流到哪」，而是**从源头禁止把资源当成普通值再绑定或传出**。`try` 资源只能「原地使用」，不能「作为值被复制/移动/返回给另一个变量」：

| 用法 | 示例 | 允许？ |
|------|------|--------|
| 原地修改内容 | `buf[0] = 65`、`*p = x` | ✅ 资源未被重新绑定，只改其指向的内容 |
| 只读传入内建/普通函数 | `print(buf)`、`length(buf)` | ✅ 传引用/值，不产生新持有者 |
| 绑定到新变量 | `var x = buf` | ❌ 编译错 |
| 赋值给块外变量 | `outside = buf` | ❌ 编译错 |
| 返回 | `return buf` | ❌ 编译错 |

```dc
// ❌ 编译错：try 资源不能绑定到新变量（含浅层洗白）
fn f() {
    var outside: []u8;
    try (var buf = allocate(128)) {
        var x = buf;        // ❌ 禁止：会产生第二个持有者
        outside = x;        // （x 逃逸即 buf 逃逸）
    }
}

// ❌ 编译错：try 资源不能返回
fn build() -> []u8 {
    try (var buf = allocate(128)) {
        return buf;
    }
}

// ❌ 编译错：try 资源不能赋给块外变量
fn f() {
    var outside: []u8;
    try (var buf = allocate(128)) {
        outside = buf;
    }
}

// ✅ 正确：原地使用
fn ok() {
    try (var buf = allocate(128)) {
        buf[0] = 65;        // 原地写入，允许
        print(buf);         // 只读传入，允许
    }
}

// ✅ 正确：需要返回/逃逸时，改用 allocate + defer/手动 free
fn build() -> []u8 {
    var buf = allocate(128);
    return buf;             // 所有权交给调用者
}
```

逃逸检查为**语法级检查**：在 `try` 块体内，只要 `try` 资源出现在「赋值左侧、作为值被绑定给新变量、或作为 `return` 值」即报错，**无需数据流分析**。「禁止重新绑定」使间接逃逸（`var x = buf; outside = x`）在源头就不成立，故不存在可绕过的中间变量盲区。

> 已知限制（悬垂引用，而非双重释放）：`var h = Holder { buf }`（把 `try` 资源作为构造器字段初值）不触发本节禁止项，但存在**悬垂引用**风险——块退出时 `defer free(buf)` 释放底层内存，而 `h` 仍持有同一指针；由于无人再次 `free(h)`，§8 的「双重释放检测」与「泄漏检测」**均无法捕获**该错误，属静默未定义行为。
>
> **首版处理**：实现 M14 时，若成本允许，建议将「`try` 资源作为构造器字段初值」同样纳入本节语法级禁止（与 `var x = buf` 同源，都产生第二个持有者）；若因 §6 结构体语义尚未回溯而暂缓，则必须在文档中将此写法**明确列为未定义行为**，不得以「Debug 双重释放检测兜底」表述——该检测不覆盖悬垂引用。

### 4.3 场景选择速查

| 场景 | 写法 |
|------|------|
| 局部申请，用完即弃 | `try (var b = allocate(n)) { ... }` |
| 局部申请，逻辑复杂/多分支 | `var b = allocate(n); defer free(b);` |
| 申请后要返回给调用者 | `var b = allocate(n); return b;`（调用者接管） |
| 申请后要存入结构体/模块状态 | `var b = allocate(n);` + 明确时机手动 `free(b)` |

心智模型：`try` 表示「这块内存活不过这个块」；`allocate`/`free`/`defer` 表示「内存生命周期由用户决定」。

## 5. 待冻结语义清单

实现前必须逐条冻结以下语义（对应 roadmap M14 的验收项）：

### 5.1 值语义与复制

- 标量（整数、浮点、布尔、字符）保持纯值语义，按位复制。
- 字符串切片 `string` 是「指针 + 长度」的 fat pointer，复制为浅拷贝（两个切片共享底层字节）。
- 动态切片 `[]T` 同样为浅拷贝语义。
- **结构体/枚举（M14 需回溯补齐）**：见 §6，必须明确含堆指针字段时的复制规则。

### 5.2 值语义（不引入移动语义）

本提案**不引入移动语义**。赋值与传参一律为复制（copy）。结构体/枚举按分量复制，指针/切片字段复制其「地址/指针+长度」本身（浅拷贝）。不存在「所有权转移」概念，因此没有 move、没有 drop。

### 5.3 显式指针（最小模型，M14 纳入）

Zig 式「引用 = 显式指针」。引入最小可用的显式指针，避免大结构体复制、支持递归/图状数据结构：

- 类型：`*T`（指向 `T` 的指针）。
- 取址：`&expr` 产生 `*T`。
- 解引用：`*expr` 得到 `T`。
- 指针取字段：`q->x`（等价于 `(*q).x`），采用 C 式 `->` 运算符，显式且简洁。
- 指针本身是值类型：赋值/传参复制地址。

```dc
var p = Point { 1, 2 };     // 值
var q: *Point = &p;         // 显式指针
q->x = 99;                  // 通过指针修改 p.x（等价 (*q).x）
var x = *q;                 // 显式解引用，得到 Point 值
```

首版约束（最小模型）：

- **指针默认非空**：声明 `*T` 必须初始化，编译器保证非空；**不引入**可选类型 `?T` 与 null（延后到 M15+，见 §9）。
- **不做悬垂检查**：编译器不证明指针指向的对象生命周期（不做借用检查）。悬垂风险由文档约定 + 运行时 trap 兜底（§8）。
- **不做指针算术**：`*T` 不可加减，仅支持取址、解引用与字段/索引访问。

实现说明：codegen 层已具备 `stack_addr`/`load`/`store` 与 `component_layout`（见 [codegen.rs](../src/codegen.rs)），显式指针仅需在词法/语法/IR 层暴露 `*`、`&`、`*T`，代码生成复用现有机制，工程量有限。

### 5.4 分配与释放

- 分配入口：内建函数 `allocate(n: usize) -> []u8`（字节切片）。
- 释放入口：内建函数 `free(s: []u8)`。
- 手动释放：用户显式调用 `free(buf)`，释放责任由「最后一个持有者」承担。
- `defer <expr>` 在所属**块作用域**退出时按 LIFO 逆序执行（通用收尾，非内存专用）。循环体视为一个块，`defer` 于每轮迭代结束时执行（见 §12.1）。
- `try (var x = allocate(n), ...) { ... }` 为 `defer` 语法糖，块内资源禁止逃逸（见 §4.2）。
- 释放顺序：同一作用域内多个 `defer`/`try` 资源按声明顺序**逆序**释放。
- 分配失败：触发运行时 trap（对齐现有 `dolphin_runtime_trap`），退出码约定见 §7。

### 5.5 切片

- 切片为 `{ ptr, len }` 二元组，无容量字段（首版简化，容量扩展延后）。
- 切片是值类型：复制切片 = 复制「指针 + 长度」两个字段，底层数据共享（浅拷贝）。
- 切片支持索引访问与越界检查（复用现有 `bounds_check` 的 trap 机制）。

### 5.6 动态数组

- 首版以「切片 + 手动管理」为最小可用形态，**不引入** `ArrayList` 式自动扩容容器（延后到 M15 标准库，避免在内存模型定型前引入隐藏所有权问题的 API）。
- 用户通过 `allocate` + 索引 + `defer free` 手写动态数组。

### 5.7 字符串所有权

- `string` 与 `[]u8` 为**别名等价（同一 `{ptr, len}` 布局）**，`string` 额外承诺内容为合法 UTF-8（见 §12.3 子问题 3a）。
- `string` 切片不拥有底层内存；静态字符串字面量指向只读数据段。
- 动态字符串 = 堆上字节 + 切片视图，由用户显式 `free`。
- 字符串拼接 `a + b` 为语法糖，隐式分配目标缓冲并返回新切片，释放责任交接收者（见 §12.3 子问题 3b）。
- 字符串比较沿用现有 `dolphin_string_equal`（按内容比较，不比较指针）。

## 6. 结构体/枚举跨函数传值（最大风险点）

这是 M13 故意留空、M14 必须补齐的核心。关键问题：**结构体含堆指针字段时，按值传递是浅拷贝还是深拷贝？**

### 决策：浅拷贝 + 显式管理

- 结构体按值传递时，逐分量平铺复制（现有 `component_layout` 已支持）。
- 堆指针字段复制指针本身（浅拷贝），**不**自动深拷贝堆内容。
- 释放责任在用户：谁分配谁释放，通过 `defer free` 显式管理。
- 禁止隐式释放：编译器**不**在结构体离开作用域时自动释放其堆字段（避免 double-free 与所有权歧义）。

### 风险与缓解

- 风险：浅拷贝后两个结构体实例持有同一堆指针，若各自 `free` 会 double-free。
- 缓解：文档明确「堆字段遵循共享视图语义，释放责任唯一归属」；配合运行时双重释放检测（§8）。
- 明确排除：本提案不实现引用计数或智能指针来消除此风险，保持最小实现。

## 7. 错误处理与退出码

沿用现有 trap 机制（[unix_runtime.c `dolphin_runtime_trap`](../runtime/unix_runtime.c)），新增：

| 错误 | 触发条件 | 退出码 |
|------|---------|--------|
| 分配失败 | `allocate` 返回失败 | 102（新增，区别于现有 101） |
| 越界 | 切片/数组索引越界 | 101（沿用） |
| 双重释放检测 | 检测到对已释放内存再次 `free` | 103（新增，Debug 模式） |

### 7.1 退出码的实现归属（实现前需冻结）

两类错误退出在实现层分属不同通道，需明确区分：

1. **越界（101）**：沿用现有 CPU trap 通道——`bounds_check` 生成 `trapnz(..., TrapCode::unwrap_user(1))`，由运行时的信号 / vectored exception handler（`dolphin_runtime_trap`）捕获。此通道**不产生**进程退出码，而是由信号/异常退出（现状 M0-M13 已如此，M14 不改变）。

2. **分配失败（102）与双重释放（103）**：`allocate`/`free` 是运行时函数，通过**普通函数返回/调用路径**报告失败，而非 CPU trap。检测到分配失败或双重释放时，运行时调用统一的 `dolphin_runtime_exit(code)` 辅助函数，以 `exit(code)`（Unix）/ `ExitProcess(code)`（Windows）显式退出，**直接产生进程退出码** 102 / 103，不经过信号通道。

> 命名提示：现有 `dolphin_runtime_trap` 承担的是「信号/异常入口」，与「显式退出码」语义不同。M14 建议新增独立的 `dolphin_runtime_exit(code)`，避免复用 `dolphin_runtime_trap` 造成「信号 trap」与「进程退出码」两套语义混在一个入口里。

## 8. 运行时检测（Debug 模式）

对齐 Zig 哲学，在 Debug 构建启用检测分配器：

- 双重释放检测：`free` 已释放的块 → trap。
- 泄漏检测：程序退出时报告未释放块（打印地址与大小到 stderr）。
- Release 构建关闭检测，追求性能。

---

## 9. 演进路径（不在 M14 实现）

以下能力明确延后，避免本里程碑过度设计：

- `Allocator` 类型与参数传递（arena/测试注入）。
- 可选类型 `?T` 与 null（可空指针、`Option` 语义，M15+）。
- 指针的悬垂检查 / 借用自动推导（如后续需要，**绝不引入 `'a` 标注**，采用自动推导或运行时检测）。
- `ArrayList`/`StringHashMap` 等自动扩容容器（M15）。
- 容量字段 `{ ptr, len, cap }` 的切片扩展。
- 循环引用处理（本提案无 RC，不存在循环引用问题）。

---

## 10. 验收标准

1. 用户可用 `allocate` + `defer free` 编写跨函数、跨模块的动态数据程序，无泄漏、无重复释放、无悬垂引用。
2. 结构体/枚举可作为函数参数与返回值（补齐 M13 留空），复制语义与 §5、§6 一致。
3. Debug 构建下，双重释放与泄漏能被运行时检测并报告。
4. 越界访问继续触发确定性 trap。
5. 全部现有 M0-M13 测试仍通过；新增 M14 示例（含跨模块容器使用）通过。

## 12. 待决清单（整理）

以下问题按风险从高到低排列。前 6 条对应 §11，7-9 为评审中补充发现的边界问题。每条给出「为什么必须现在定」与「建议的默认决策」，供评审逐条拍板。

### 12.1 循环体内 `defer` 的作用域（对应 §11.3）— ✅ 已确定：块作用域

- **决策**：`defer <expr>` 绑定**块作用域**（对齐 Zig）。`defer` 在所属 `{}` 块退出时执行；循环体本身视为一个块，因此每轮迭代结束时释放。若用户需要「整个循环共享一块、出循环再释放」，把 `defer` 写在循环体外的外层块中即可，语义自然且无额外语法。
- **理由**：若绑定函数作用域，`while`/`loop` 体内每轮迭代的 `defer free(buf)` 会累积，直到函数退出才统一执行，导致内存持续增长、释放顺序语义混乱；块作用域语义自然，且无需新增语法即可覆盖两种用法。

### 12.2 `try` 资源逃逸检查的边界（对应 §11.4）— ✅ 已确定：禁止重新绑定/传播

- **决策**：`try` 资源在块内采用「**禁止重新绑定/传播**」规则——资源只能原地使用（原地写入、只读传入），不能作为值被绑定给新变量（`var x = buf`）、赋值给块外变量（`outside = buf`）或返回（`return buf`）。三者均编译报错，检查为语法级，无需数据流分析。
- **理由**：相比「直接引用检查」，此规则从源头禁止 `var x = buf` 成立，故「中间变量洗白」这类间接逃逸在结构上即不存在，无需追踪数据流、也不存在可绕过的盲区；同时与 §4.2「语法级检查」定位一致，实现更简单。相比「局部数据流追踪」，它不制造「看起来安全却仍堵不住跨函数/容器/字段逃逸」的虚假安全感。
- **已知限制（悬垂引用，而非双重释放）**：`var h = Holder { buf }`（资源作为构造器字段初值）不触发本节禁止项，但存在**悬垂引用**风险——块退出时 `defer free(buf)` 释放底层内存，而 `h` 仍持有同一指针；由于无人再次 `free(h)`，§8 的「双重释放检测」与「泄漏检测」**均无法捕获**，属静默未定义行为。首版建议将其纳入语法级禁止（与 `var x = buf` 同源，都产生第二个持有者）；若暂缓，则必须将此写法**明确列为未定义行为**，不得以「Debug 双重释放检测兜底」表述——该检测不覆盖悬垂引用。

### 12.3 动态字符串与字节切片的关系（评审新增，最高风险）

- **子问题 3a：`string` 与 `[]u8` 的关系** — ✅ 已确定：**别名等价（同一布局）**。`string` 内部同 `[]u8` 的 `{ptr, len}` 布局，唯一区别是 `string` 承诺内容为合法 UTF-8；`free` 与 `allocate` 直接复用字节切片通道，无需额外转换语法或 `free_str`。

  **索引语义需一并冻结**：`string` 与 `[]u8` 布局等价，但**类型系统上仍是两个不同类型**——`string` 保持 M8 冻结的「不可索引」约束（不可下标），`[]u8` 支持索引访问（§5.5）。二者仅在 `free`/`allocate` 通道、函数传参 ABI 与内存布局上等价，不意味着 `string` 获得下标能力。若用户需要按字节读写字符串内容，须显式转换为 `[]u8`（具体转换语法在 M14 实现时冻结，或沿用 M15 泛型切片转换方案）。
- **子问题 3b：字符串拼接（`a + b`）的分配方式** — ✅ 已确定：**糖内隐式 `allocate`（受控例外）**。`+` 作为语法糖，展开为「隐式 `allocate` 目标缓冲 + `string_concat(目标, a, b)` + 返回目标切片」，从而保留 `var c = a + b` 一行式语法。释放责任交接收者（谁接收谁 `free`）。
- **受控例外的边界（必须一并冻结）**：
  1. `+` 是**唯一**的隐式分配点。其余所有动态内存仍走显式 `allocate`；不得再新增其他隐式分配运算符或内建函数。
  2. 释放仍为**确定性显式**：`+` 的结果不自动释放，必须由「最后一个持有者」显式 `free`（或纳入 `defer`/`try`）。`+` 只隐式了「分配」，**没有**隐式了「释放」。
  3. `+` 返回的切片遵循 §5.1 浅拷贝语义：赋值/传参复制 `{ptr, len}`，底层字节共享，释放责任唯一归属（配合 §8 Debug 双重释放检测兜底）。
  4. 拼接失败（如分配失败）沿用 §7 的 102 trap，不产生部分可用的字符串。
- **理由**：与 `try` 语法糖同构——把「易用性优先」（§2 原则 1）落实为语法糖，同时以「唯一隐式分配点 + 显式释放」最小化对原则 3「显式控制、确定性释放」的偏离。相比零隐式分配路线（放弃一行式语法），更贴合面向学习/实践的语言定位；相比 GC/引用计数路线，不推翻 §3 冻结的显式分配路线。

### 12.4 `allocate` 返回类型（对应 §11.1）— ✅ 已确定：首版返回 `[]u8`

- **决策**：首版 `allocate(n: usize) -> []u8` 返回**字节切片**，不追求泛型化。泛型 `[]T` 的 `allocate` 属 M15 演进项，届时 `[]u8` 语义平滑迁移。已确定。
- **理由**：首版无泛型，字节切片是唯一可行的统一分配入口；配合 §12.3 的 `string`/`[]u8` 别名等价，`allocate` 同时是动态字符串与动态数组的共同地基，无需为字符串单开分配入口。M15 引入泛型时按「`allocate<T>(n) -> []T`」演进，字节切片即 `allocate<u8>` 的特例，迁移平滑。

### 12.5 `allocate`/`free` 内建符号如何进入多模块链接（评审新增）— ✅ 已确定：复用内建函数接入机制

- **决策**：复用现有内建函数接入机制——`allocate`/`free`（及拼接所需的 `string_concat`）作为运行时导出符号，通过 `platform.c_symbol(name)` 名称映射 + `declare_function(..., Linkage::Import, ...)` 声明为 Import 符号（见 [codegen.rs](../src/codegen.rs) `RuntimeIds`），运行时在 `runtime/unix_runtime.c` / `runtime/windows_runtime.cpp` 中导出对应符号。不新造分发通道。已确定。
- **理由**：与 `dolphin_string_equal`、`dolphin_print_*` 完全同一套接入方式，天然满足「多模块链接使用稳定符号」这一 M7 约束；跨模块调用与单文件调用在 codegen 层无差别，验收标准 1（跨模块动态数据）无需额外链接逻辑。

### 12.6 双重释放检测的实现粒度（对应 §11.2）— ✅ 已确定：header 标记 + 存活登记表 + 退出钩子

- **决策**：首版 Debug 检测分配器采用「**header 标记 + 存活登记表 + 退出钩子**」三件套，不引入完整 general-purpose allocator。已确定。

  1. **header 标记（双重释放检测）**：`allocate(n)` 实际分配 `sizeof(header) + n` 字节，在用户数据区之前放一个 header，含「存活魔数」与「块大小」。`free(buf)` 拿到的 `buf.ptr` 是数据区起始，内部往前偏移 `sizeof(header)` 定位 header；若魔数已被置为「已释放」态，`free` 判定为双重释放 → trap（退出码 103）。释放时把魔数改写为「已释放」态，防止再次 `free`。
  2. **存活登记表（泄漏检测）**：运行时维护一个存活块登记表（链表/动态数组均可），`allocate` 时登记「数据区地址 + 块大小」，`free` 时移除。程序退出时遍历登记表，把每个未释放块的地址与大小打印到 stderr。header 与登记表**分工明确**——header 只管「双重释放判断」，登记表只管「泄漏报告」，不冗余；两者通过同一 `free` 路径同步（先校验 header 魔数、再移除登记表项）。
  3. **退出钩子**：泄漏报告需要「程序退出时」触发。复用现有运行时的初始化钩子对称机制——Unix 用 `__attribute__((destructor))`（对齐现有 `dolphin_install_traps` 的 constructor，见 [unix_runtime.c](../runtime/unix_runtime.c)）；Windows 用静态对象析构函数（对齐现有 `TrapInstaller` 静态对象，见 [windows_runtime.cpp](../runtime/windows_runtime.cpp)）。仅 Debug 构建链接该钩子；Release 构建不链接，且不生成 header/登记表（`allocate` 直接裸 `malloc`）。
  4. **Release 行为**：关闭检测 = 不做这些检查。`allocate` 直接 `malloc`，`free` 直接 `free`，无 header、无登记表、无退出钩子；错误用法（双重释放、泄漏）属未定义行为，不保证检测。

- **理由**：以最小工程量覆盖验收标准 3 的两项（双重释放、泄漏）检测。header 与登记表职责分离、无信息冗余；退出钩子直接复用运行时既有的 constructor/静态对象机制，Unix/Windows 各加一个对称的 destructor/析构函数即可。完整 allocator（红黑树等）留作 M15 演进，不在 M14 引入。

### 12.7 `&s.field` 字段地址的生命周期约束（对应 §11.6）— ✅ 已确定：文档约定安全子集

- **决策**：首版**不做**悬垂检查，采用「文档约定安全子集 + Debug 不检测」。已确定。

  约定安全子集写入文档，明确以下三类为**安全用法**：

  1. 取址结果只在**被取址对象保持存活且未被重新赋值期间**使用；
  2. 取址主要用于「避免大结构体复制」（传参）与「字段就地修改」，**不鼓励长期持有**；
  3. **禁止取临时值的字段地址**（如 `&(make_point()).x`）——临时值在表达式结束时即销毁，其字段地址立即悬垂。

  同时明确：跨作用域持有 `&s.field`、或对被重新赋值的对象继续使用旧地址，属**未定义行为**，Debug 模式**不检测**、由运行时 trap 兜底（§8）。

- **理由**：首版「不做悬垂检查」已冻结（§5.3），无法静态证明安全；提供一个可执行的安全子集让验收标准「无悬垂引用」有明确定义。补充「禁止临时值字段地址」一条，堵住比「重新赋值」更隐蔽的悬垂来源。

### 12.8 `defer`/`try` 释放顺序的精确语义（评审新增）— ✅ 已确定：声明/展开顺序的逆序

- **决策**：统一以「**声明/展开顺序的逆序**」为唯一基准。`try (a, b) { ... }` 等价于依次 `defer free(a); defer free(b);`，出块时 `free(b)` 再 `free(a)`（LIFO）；与块内显式 `defer` 按时间顺序统一压栈、统一逆序弹出。已确定。
- **理由**：`try` 语法糖展开后与显式 `defer` 采用同一「逆序弹栈」模型，无二义、可预测，且与 §12.1 的块作用域语义自然一致。

### 12.9 分配失败与 Debug/Release 行为的一致性（评审新增）— ✅ 已确定：102 恒定、103 仅 Debug

- **决策**：分配失败（退出码 102）在 Debug/Release 下**始终 trap**，与检测开关无关；双重释放检测（103）仅在 Debug 启用。已确定。

  具体规则：

  1. `allocate` 分配失败 → trap，退出码 **102**，Debug/Release 均成立（检测开关不影响 102 的确定性）。
  2. 双重释放检测 → trap，退出码 **103**，**仅 Debug** 可达；Release 关闭检测后不做该检查，双重释放属未定义行为。
  3. Release 关闭检测 = **不做这些检查**（header/登记表/退出钩子全部不生成，见 §12.6），错误用法（双重释放、泄漏、越界之外的悬垂访问）行为未定义，不保证 trap。

- **理由**：区分「错误 trap」（102/101，与检测无关、恒成立、可测试）与「检测报告」（103，Debug 专属）两类语义，避免 Release 下行为漂移，确保 102/101 在两种构建下稳定可测。
